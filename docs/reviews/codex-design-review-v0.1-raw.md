**세이브 계보와 스레드**

1. **[치명] 세이브 전체의 확정·복구 프로토콜이 없습니다.**  
   **위치·확인:** §5.2, `D:151`, `D:160`. 조각을 먼저 확정한 뒤 co-save를 쓰고 즉시 부모를 전진시킵니다. 직렬화 쓰기 API는 성공 여부를 반환하지만 그 처리도 없습니다(`C/include/SKSE/Interfaces.h:255`, `:266`).  
   **위험·조건:** 조각 이동 후 co-save 쓰기가 실패하거나 종료되면 외부 기록과 게임 세이브가 어긋납니다. 실패한 저장의 조각이 다음 저장의 부모가 되는 경우, 그래프는 연결되더라도 모든 노드가 성공한 세이브라는 의미는 성립하지 않습니다. SKSE 소스에서도 co-save 생성 실패 시 콜백 전 반환하는 경로가 있습니다. [Serialization.cpp](https://github.com/ianpatt/skse64/blob/master/skse64/Serialization.cpp#L335)  
   **반대 근거·보완:** 실패 후 계속 플레이한 사건을 보존하는 것은 타당합니다. 다만 저장 시도·준비된 조각·공개 가능한 조각을 구분하고, 재시작 시 조각/co-save 불일치를 어떻게 판정할지 정해야 합니다. DLL이 `.ess`와 `.skse`까지 하나의 원자적 트랜잭션으로 만들 수 있다고 약속해서도 안 됩니다.

2. **[치명] flush 타임아웃 때 “다음 조각으로 넘긴다”는 대응은 세이브 경계를 깨뜨립니다.**  
   **위치·확인:** §4.2·5.2·12, `D:118`, `D:151`, `D:388`.  
   **위험·반례:** 저장 A 이전 사건 E가 밀려 다음 조각 B에 들어간 뒤 A를 로드하면, A의 게임 상태에는 E의 결과가 있는데 A의 이야기에는 E가 없습니다. 타임아웃 후에도 기존 writer가 파일을 쓰는 중이라면 이름 변경과 새 pending 전환도 경합합니다.  
   **반대 근거·보완:** 대기 상한은 필요합니다. 그러나 **사건의 소속 세이브를 뒤로 미루는 것과 디스크 기록 완료를 늦추는 것은 다릅니다.** 저장마다 사건 cutoff를 고정하고, 늦게 기록되더라도 원래 조각에 귀속시키는 계약이 필요합니다.

3. **[높음] `revert`를 포함한 전체 수명주기 상태표가 없습니다.**  
   **위치·확인:** §5.2, `D:150`–`157`에 revert·메인 메뉴 상태가 없습니다. API에는 별도 revert 콜백이 있고(`C/include/SKSE/Interfaces.h:261`), upstream은 VM의 revert 후 이를 호출합니다. [Hooks_Papyrus.cpp](https://github.com/ianpatt/skse64/blob/master/skse64/Hooks_Papyrus.cpp#L306)  
   **위험·조건:** A 캐릭터 → 메인 메뉴 → B 캐릭터, 새 게임 재시작, 로드 중 revert에서 캐릭터 ID·전투 집계·동료 목록·미완료 작업이 섞일 수 있습니다. `kNewGame` 또는 정상 로드만 기다리는 초기화는 콘솔 `coc` 시작 경로도 설명하지 못합니다.  
   **반대 근거·보완:** 일반적인 새 게임/로드 경로는 표로 처리할 수 있습니다. `Idle/Playing/Loading/RecordingDisabled` 같은 상태와 각 콜백의 허용 전이를 명시하고, `coc`에서 실제 어떤 신호가 오는지는 0단계의 별도 시험으로 남겨야 합니다.

4. **[높음] 로드 실패 시 “이전 상태 유지”의 범위가 잘못 정의되어 있습니다.**  
   **위치·확인:** §5.2, `D:152`–`155`. pending 파일만 되돌리는 설명입니다.  
   **위험·반례:** 로드 중 VM revert나 게임 상태 변경이 이미 진행된 뒤 실패했다면, DLL의 이전 actor 참조·장소·전투 상태까지 복원해 정상 플레이로 간주할 근거가 없습니다. 이전 UUID만 복원해도 게임 상태가 복원되지는 않습니다.  
   **반대 근거·보완:** 외부 pending과 이전 계보 메타데이터를 보존하는 것은 맞습니다. **파일 복구와 게임 객체 상태 재사용을 분리**하고, 재개 가능한 게임 상태가 확인되지 않으면 기록을 정지해야 합니다. SKSE도 로드 실패 후 플러그인 상태 재설정을 별도로 요구합니다. [PluginAPI.h](https://github.com/ianpatt/skse64/blob/master/skse64/PluginAPI.h#L195)

5. **[높음] 콜백 인자·스레드·세이브 이름 획득 계약이 빠졌습니다.**  
   **위치·확인:** §4.2·5.2, `D:118`, `D:151`, `D:154`. 직렬화 콜백은 `SerializationInterface*`만 받고 세이브 이름을 받지 않습니다(`C/include/SKSE/Interfaces.h:255`). `BGSSaveLoadManager`에는 별도 스레드와 비동기 큐도 있습니다(`C/include/RE/B/BGSSaveLoadManager.h:76`, `:93`).  
   **위험·조건:** “게임 스레드”라는 가정만으로 공유 상태를 무잠금 접근하거나, 직렬화 콜백에서 세이브 이름을 얻는다고 구현하면 잘못될 수 있습니다. `kPostLoadGame`의 성공 값도 포인터가 가리키는 bool이 아니라 포인터 값으로 전달되는 upstream 구현입니다.  
   **반대 근거·보완:** 메시지의 `kSaveGame`에서 이름을 복사해 둘 수 있습니다. 이는 저장 완료 통지가 아닙니다. 이름 복사 시점, 성공 값 해석, 각 콜백의 실제 thread ID와 순서를 1.6.1170에서 계측해야 합니다. [Hooks_SaveLoad.cpp](https://github.com/ianpatt/skse64/blob/master/skse64/Hooks_SaveLoad.cpp#L11)

6. **[높음] 세대 번호만 올려서는 로드 중 사건과 늦은 사건을 모두 거를 수 없습니다.**  
   **위치·확인:** §5.2, `D:152`; 공통 필드 `D:102`–`108`에는 generation도 없습니다.  
   **위험·반례:** 로드 중 발생한 사건이 이미 증가한 “현재 세대”를 읽으면 정상 사건처럼 통과합니다. 이전 세대에서 예약한 `AddTask`가 실행 시점에 새 세대를 읽어도 같은 문제가 납니다. 같은 세이브 반복 로드는 `saveUid`만으로 구별되지 않습니다.  
   **반대 근거·보완:** 세대 번호는 적절한 수단입니다. 다만 사건 최초 관측 시 캡처한 세대, 명시적인 수집 허용 상태, task 실행 전·enqueue 전 검사, 로드 실패 후 새 세대에서의 재개 규칙까지 있어야 합니다.

7. **[높음] MPSC 큐의 순서와 `seq`·저장 cutoff의 관계가 없습니다.**  
   **위치·확인:** §4.1·4.2·5.2, `D:103`, `D:115`, `D:117`, `D:151`.  
   **위험·반례:** 생산자 P가 seq 10을 할당하고 지연되는 동안 Q가 11을 enqueue하고 저장 barrier가 들어가면, 단순 FIFO flush로 10까지 모두 확정됐다고 말할 수 없습니다. 이름 해석 task가 저장 이후 끝나는 경우도 같습니다.  
   **반대 근거·보완:** 단일 게임 스레드에서 모두 완성해 enqueue한다면 단순해집니다. 현재는 MPSC와 지연 task를 함께 허용하므로, 순서 결정 시점·진행 중 생산자·미해석 사건의 처리까지 규정해야 합니다.

8. **[높음] 큐 포화 정책이 중요한 사건과 제어 메시지를 보호하지 못합니다.**  
   **위치·확인:** §4.2, `D:115`. 낮은 우선순위를 합치거나 버린다는 설명뿐입니다.  
   **위험·조건:** 큐가 이미 중요한 사건으로 찼거나 flush/seal 명령을 같은 큐에 넣어야 하면 어떻게 되는지 없습니다. 전투 시작 또는 종료 한쪽만 버리면 이후 집계도 틀립니다. “버린 개수” 자체가 같은 큐에서 유실될 가능성도 있습니다.  
   **반대 근거·보완:** 제한 큐는 맞습니다. 제어 경로 예약, 우선순위별 허용 손실, 쌍을 이루는 사건의 처리, 계보별 누락 표식, 바이트 단위 메모리 상한까지 필요합니다.

9. **[높음] writer가 게임 스레드를 직접 기다리지 않는다는 조건만으로 교착을 배제할 수 없습니다.**  
   **위치·확인:** §4.2, `D:118`.  
   **위험·반례:** save 콜백이 상태 mutex를 잡고 flush를 기다리고 writer가 같은 mutex를 얻어야 완료한다면 교착입니다. writer의 예외·종료로 완료 신호가 누락되는 경로도 없습니다. 타임아웃 후 살아 있는 writer와 새 파일 작업의 소유권 문제도 남습니다.  
   **반대 근거·보완:** 객체 포인터를 writer로 넘기지 않는 원칙은 좋습니다. 잠금 순서, 대기 중 보유 금지 잠금, 제어 요청별 완료 결과, writer 장애 시 기록 중지, 종료 시 join/취소 정책이 필요합니다.

10. **[높음] 싱크 안 조회의 안전성·비용과 사건별 필터가 정의되지 않았습니다.**  
    **위치·확인:** §4.2, `D:112`–`117`. `BSTEventSource::SendEvent`는 lock을 잡고 sink를 동기 호출합니다(`C/include/RE/B/BSTEvent.h:131`).  
    **위험·조건:** 저널 생성·이름 조회·동료 판정·문자열 할당이 모두 50µs 목표 안에 들어간다는 근거가 없습니다. 이 lock은 게임 객체 전체를 보호하는 lock도 아닙니다. 퀘스트·발견 이벤트에는 actor 필드가 없으므로 “먼저 플레이어/동료 관련인지 확인”을 공통 적용할 수 없습니다.  
    **반대 근거·보완:** 작은 값 복사는 합리적입니다. 사건별 호출 스레드, 안전한 즉시 복사 필드, 후속 해석 필드, 실패 시 `unknown` 처리, 캐시 무효화 규칙을 나눠야 합니다.

11. **[높음] `activeHead` 갱신 규칙이 본문 사이에서 불일치합니다.**  
    **위치·확인:** §5.2의 저장 처리 `D:151`에는 `character.json` 갱신이 없고, §7.2 `D:242`는 마지막 저장 또는 로드라고 합니다. `D:230`은 다시 “가장 최근 세이브”라고 설명합니다.  
    **위험·반례:** A 로드 → B 저장 → 종료에서 디스크의 머리가 A로 남으면 EXE가 B를 쓰지 않습니다. 반대로 실패한 저장을 머리로 공개하면 존재하지 않는 저장을 기본값으로 삼습니다.  
    **반대 근거·보완:** 최근 파일 시각보다 `activeHead`를 쓰는 결정은 맞습니다. 저장·로드·기록 없음·실패별 갱신 시점과 revision을 단일 규칙으로 정해야 합니다.

12. **[높음] 중간 조각이 없을 때 “남은 조상까지 잇기”는 현재 자료만으로 불가능할 수 있습니다.**  
    **위치·확인:** §5.1·5.2·6, `D:141`, `D:157`, `D:177`. 부모 정보는 co-save와 조각 머리말에 있습니다.  
    **위험·반례:** S → B → A에서 B 파일이 사라지고 B의 co-save도 없다면, S 파일로 B라는 ID는 알아도 B의 부모 A를 알아낼 수 없습니다. 순환·다른 캐릭터 부모·중복 UID·변조된 머리말 검증도 없습니다.  
    **반대 근거·보완:** S 자신의 조각만 없고 co-save에 부모가 남아 있는 경우에는 복구 가능합니다. 복구 가능한 경우를 구분하고, 독립 계보 인덱스 또는 끊긴 지점에서 중단하는 정책을 정해야 합니다.

13. **[높음] pending·discarded의 복구와 분기 식별 정보가 부족합니다.**
